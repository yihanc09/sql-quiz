# SQL Quiz — Vercel Deployment

This repository deploys the SQL Quiz frontend and Python API to Vercel. The canonical coursework repository is [yihanc09/IDS706-SQL-Quiz](https://github.com/yihanc09/IDS706-SQL-Quiz). Runtime code, data contracts, tests, and supporting documentation are synchronized from that project.

This repository contains my Week 7 SQL quiz and its Week 8 RAG extension. Both use the same Chinook music-store database in Supabase. Students can write their own SQL, inspect live results, and save their progress. The Week 8 addition lets them ask a question and get SQL generated from knowledge retrieved through ChromaDB.

## Project overview

An interactive SQL practice application for **IDS706 Data Engineering**, built with an independent HTML/CSS/JavaScript frontend, a Python backend, and Supabase PostgreSQL. Students explore the Chinook Music Store database, work through five business questions worth **20 points**, and receive feedback based on live query results. Week 8 adds RAG-powered SQL generation to the same workspace.

### Key features

- **Independent frontend:** Duke Blue styling, responsive navigation, and dedicated dataset guide, question, and results pages.
- **Authentication:** Sign up, sign in, and sign out through Supabase Auth. Query execution and saved work require authentication.
- **Dataset reference:** All eleven Chinook tables are available in the Schema toolkit, with column types and relationships. The tables relevant to each question appear first.
- **Question-specific hints:** The Hint toolkit explains joins, aggregation, and sorting, and provides reference SQL with live expected results. Hint, Knowledge, and Schema sit beside the editor on larger screens and open in a panel on smaller screens.
- **SQL editor:** Per-question drafts, line numbers, tab indentation, and Ctrl/Cmd + Enter to run a query.
- **Interactive execution:** Read-only PostgreSQL queries return a visible result table before submission.
- **Automatic grading on submission:** Each question earns zero or four points based on returned columns, values, and required row order.
- **Persistent progress:** Save drafts and graded submissions in Supabase and restore them after signing in again.
- **Results dashboard:** Review each question's status and the total score out of 20, then revisit an answer.
- **RAG SQL generation:** Ask a question in Knowledge, inspect actual Chroma retrieval sources, and review SQL generated by OpenAI before using it in the editor.
- **Parameterized application SQL:** Bind values separately from SQL text for audit writes, configuration lookups, and permission checks.
- **Audit logging and integrity checks:** Record who ran or saved SQL and verify that student-facing roles cannot directly read, insert, modify, delete, or truncate audit records.

### Week 7: sign in, run SQL, and compare results

1. Open the site. Visitors can browse the dataset guide and questions, but running queries and saving work require sign-in.
2. Choose **Sign in**, or **Create account** to register with your own email. Confirm your email first if Supabase requests it. No shared account or password is included in this repository.
3. Open **Count Artists** and enter:

   ```sql
   SELECT COUNT(*) AS total_artists
   FROM public.artist;
   ```

4. Click **Run query**. The result table should show `total_artists = 275` for the uploaded dataset.
5. Open **Hint → Reference SQL & expected result → Load live reference**. This shows the instructor SQL and executes it against the same live database. Every question has this reference view.
6. Click **Save draft** to keep your SQL, or **Submit answer** to grade it and save the score. Open **Quiz results** to review progress. Saved drafts and grades are restored after signing out and back in.

The quiz grades returned columns, values, and any required row ordering. It does not require students to reproduce the reference SQL word for word. Unsaved edits stay in browser memory; save before refreshing or closing the page.

### Week 8: ask a question and generate SQL

1. While signed in, open a quiz question and select **Knowledge** in the question's toolkit.
2. Keep the suggested natural-language question, or enter one yourself—for example, “How many artists are there in the database?”
3. Click **Generate SQL**. The backend retrieves five relevant knowledge documents from Chroma Cloud, then sends the question and those documents to OpenAI.
4. Review the generated SQL and retrieved sources. The retrieval details identify the backend, embedding model, and collection information. **Search knowledge only** lets you inspect retrieval separately.
5. To try the SQL, choose **Use in editor**, then **Run query**. **Submit answer** compares it with the expected result for the currently selected quiz question.

Generation leaves execution and submission to the user. An unrelated natural-language question can still produce SQL, but submitting that SQL checks it against the selected quiz question, not against a new AI-created answer key.

### SQL parameters and execution safety

Application-owned SQL passes data separately from SQL text. Audit fields such as user IDs, action names, question IDs, and submitted SQL are bound through psycopg parameters. Submission persistence uses structured Supabase API payloads.

For example, the shared reader supports bound values:

```python
from sql_quiz.database import run_query

result = run_query(
    "SELECT %s::text AS value",
    ("a value containing ' quotes",),
)
```

Students intentionally submit complete SQL statements; a whole statement cannot be bound as a value. Those statements run through the independent `quiz_reader` connection with these controls:

- A read-only transaction.
- A ten-second statement timeout and a 500-row result limit; larger results are rejected with a request to add `LIMIT`.
- Application checks for a single SELECT/CTE-style statement.
- Driver preparation that rejects stacked statements, including two SELECTs, even when called outside the UI.
- Database permissions that keep student submissions, audit records, and private runtime settings away from the query reader.

Role identifiers in administrator checks use `psycopg.sql.Identifier`. These controls support classroom SQL practice; they do not provide a complete sandbox for arbitrary SQL.

### Audit logging and integrity

#### What is recorded

Audit entries in `public.quiz_audit_log` contain:

| Field | Description |
|---|---|
| `id` | Audit entry identifier |
| `user_id` | Supabase user UUID |
| `action` | Run, submit, save, or update event |
| `question_id` | Quiz question identifier |
| `created_at` | Timestamp with time zone |
| `success` | Execution/save status; older records may have no status |
| `sql_answer` | SQL text for new backend and answer-trigger events |
| `source` | How the event was recorded |

| Source | Actions | Meaning |
|---|---|---|
| `server` | `RUN_QUERY`, `SUBMIT_QUERY` | Execution observed by the Python backend; identity comes from a verified Supabase user token. |
| `answer_trigger` | `SAVE_ANSWER`, `UPDATE_ANSWER` | Recorded by the database in the same transaction as the saved answer. |
| `client_rpc` | Legacy query events | Client-reported metadata retained for compatibility; not proof of execution. |
| `legacy` | Historical events | Predates source tracking; missing historical SQL is not reconstructed. |

Successful and failed executions are logged. SQL rejected before execution is not an executed-query event. `SUBMIT_QUERY.success` describes execution success, not whether an answer earned points; grades are stored in `public.quiz_submissions`.

Saving revised SQL appends an event with the new SQL. Saving an unchanged graded answer is a no-op. Audit failures are reported separately from query/grade failures. Query execution and its audit INSERT use separate connections, so they are not atomic; saved-answer changes and their trigger-generated events are atomic.

#### How the log is protected

- RLS is enabled on the audit table.
- Direct audit-table privileges are revoked from `quiz_reader`, `authenticated`, `anon`, and `PUBLIC`.
- Students cannot directly read, insert, update, delete, or truncate audit records.
- The answer trigger uses a `SECURITY DEFINER` function with a fixed empty `search_path`; students cannot invoke it directly.
- Additional triggers reject UPDATE, DELETE, and TRUNCATE on the log.
- The trusted backend writes new query events using parameterized SQL.
- The legacy RPC derives identity from `auth.uid()`. It cannot accept another user's identity or forge `server` / `answer_trigger` sources.

#### Verify protections and inspect entries

```bash
python -m scripts.admin.audit_admin --check
python -m scripts.admin.audit_admin --recent 20
```

The checker verifies effective privileges, administrative role flags, ownership, RLS, enabled triggers, and function execution privileges. It attempts UPDATE, DELETE, and TRUNCATE using the real taker connection and administrator-switched `authenticated` / `anon` roles. All probes force a transaction rollback. Only SQLSTATE `42501` permission denials count as successful blocks; unrelated errors do not count as a pass.

`--recent` accepts a limit from 1 to 100 and includes submitted SQL in its output. These commands use the trusted backend connection; integrity checks also retrieve the independent reader connection from private settings or a legacy environment override. There is no student-facing audit-log endpoint. The administrator integrity checker runs separately from pytest and CI.

### How the RAG pipeline works

```text
Natural-language question entered in the quiz
    ↓
OpenAI text-embedding-3-small: question → 1536-dimensional vector
    ↓
Chroma Cloud: cosine vector search → top 5 knowledge documents
    ↓
Question + retrieved documents → OpenAI Responses API (gpt-4.1-mini)
    ↓
Generated PostgreSQL + source references shown in the Knowledge tab
    ↓ optional user actions
Use in editor → Run query → Submit answer
                   ↓              ↓
           Supabase result    Live reference comparison
```

The knowledge corpus contains **17 documents**: eleven table schemas, four business/SQL rules, and two independent question-and-SQL examples. It includes columns, relationships, and rules such as how to calculate track duration and sales quantities. The five instructor solutions, student submissions, and audit records are excluded from this corpus.

The documents live in [knowledge/documents.jsonl](knowledge/documents.jsonl); their vectors are stored in Chroma. The cloud collection, `chinook_knowledge_openai3small_v1`, uses `text-embedding-3-small` for both indexing and retrieval. Business rows remain in Supabase. OpenAI receives the question and retrieved knowledge to generate SQL; it does not execute the query.

Retrieval checks the collection's model, dimensions, readiness, and corpus fingerprint. If cloud retrieval fails, generation reports an error rather than silently switching to a prompt without retrieval. A separate local Chroma option uses MiniLM embeddings; [the local guide](docs/guides/chroma-local.md) explains that setup.


## Run the application locally

Use Python **3.12**, the version used in CI and deployment. The HTML/CSS/JavaScript frontend needs no Node.js build step.

### 1. Install and configure

```bash
git clone https://github.com/yihanc09/IDS706-SQL-Quiz.git
cd IDS706-SQL-Quiz
python3.12 -m venv .venv-cloud
source .venv-cloud/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

Fill in `.env` with your own backend settings:

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Trusted backend connection through the Supabase **Session pooler**, port `5432`, with `sslmode=require`; leave the password out of the URI. |
| `DATABASE_PASSWORD` | Password passed separately to the backend database connection. |
| `CHROMA_MODE` | Set to `cloud` for the cloud workflow described here. The example file defaults to local mode. |
| `CHROMA_API_KEY` | Chroma Cloud API key. |
| `CHROMA_TENANT` | Tenant from the Chroma Cloud Connect panel. |
| `CHROMA_DATABASE` | Chroma Cloud database name. |
| `CHROMA_HOST` | Hostname shown in Connect; the template uses `api.trychroma.com`. |
| `CHROMA_CLOUD_COLLECTION` | Application collection; default `chinook_knowledge_openai3small_v1`. |
| `OPENAI_API_KEY` | OpenAI API key for cloud embeddings and SQL generation. |
| `OPENAI_MODEL` | SQL-generation model; default `gpt-4.1-mini`. |

The existing Supabase project stores its Auth settings, restricted `QUIZ_DATABASE_URL`, and session encryption key in the backend-only `quiz_private.runtime_config` table. Student SQL uses that separate reader connection, not the administrator connection.

**For a new Supabase project:** configure Auth, load the eleven tables, create the restricted reader, and apply submission/audit permissions before starting the quiz. Copying `.env.example` alone does not provision these resources. Follow [setup and operations](docs/guides/setup-and-operations.md) and [live database setup](docs/reference/live-database.md) for the maintenance commands and their prerequisites.

Keep `.env`, API keys, and database passwords private. `.env` files, private exports, and generated vector storage are ignored by Git; credentials stay on the backend.

### 2. Initialize private settings and database protections

For the existing project, private settings contain `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `QUIZ_DATABASE_URL`, and `APP_SESSION_KEY`. Only the trusted backend can read them. Initialize once from an already configured checkout:

```bash
python -m scripts.admin.configure_runtime --init
python -m scripts.admin.configure_runtime --check
```

Initialization applies [002_runtime_configuration.sql](sql/002_runtime_configuration.sql), imports existing Auth/reader settings, and generates a session encryption key if needed. It uses bound parameters, does not print credentials, and preserves existing private settings. Legacy environment overrides remain supported and take precedence.

If the required settings exist only in this project's ignored local backup, the initializer can read it without replacing the current backend connection:

```bash
python -m scripts.admin.configure_runtime --init --from-env .local/backups/.env.old
```

That backup is a workstation-only file, not part of a fresh clone. Do not remove the original settings before initialization. This command does not create a complete Auth application or reader role for a new Supabase project.

For an existing compatible database that has not received the audit/submission migrations:

```bash
python -m scripts.admin.audit_admin --apply
python -m scripts.admin.audit_admin --check
python -m scripts.admin.configure_submissions --apply
python -m scripts.admin.configure_submissions --check
```

`--apply` commands change the database selected by `DATABASE_URL`, including a shared database if configured. The audit migration retains existing audit records and hardens permissions. [003_submission_storage.sql](sql/003_submission_storage.sql) creates student submission storage with per-user RLS and audit triggers. The removed legacy `quiz_answers` table is not required or recreated. These commands target the project's existing Auth/audit setup; review [setup prerequisites](docs/guides/setup-and-operations.md) before applying them to another database.

### 3. Prepare the cloud index

For your own collection, index the committed knowledge once:

```bash
python -m scripts.rag.index_knowledge --cloud
python -m scripts.rag.check_cloud
```

Indexing calls OpenAI embeddings and writes to the configured Chroma collection. It is not needed on every startup. Reindex after intentionally changing the knowledge corpus. See [Chroma Cloud setup](docs/guides/chroma-cloud.md) for configuration checks and [SQL generation setup](docs/guides/sql-generation.md) for the AI connection.

For local Chroma instead, use a separate environment with `requirements/local.txt` and follow [the local retrieval guide](docs/guides/chroma-local.md). Do not install `chromadb` and `chromadb-client` together: they share the same Python import namespace.

### 4. Start the website

```bash
python web_server.py --port 8001
```

Open [http://localhost:8001](http://localhost:8001), sign in, and follow the walkthrough above. The listener binds only to `127.0.0.1`; stop it with Ctrl+C. Restart after Python backend changes; refreshing loads changed frontend files. Without `--port`, the default is `8000`.

Locally, login uses an HttpOnly, SameSite cookie backed by process memory, with a 12-hour expiration. Restarting the listener clears local sessions. On Vercel, sessions use encrypted HttpOnly, Secure, SameSite cookies so another function instance can restore the session. Saved answers and grades remain in Supabase in either case.

### 5. Original Streamlit interface (optional)

```bash
python -m streamlit run app.py
```

Open the URL printed in the terminal, usually [http://localhost:8501](http://localhost:8501). Both interfaces share authentication, query execution, question definitions, and grading modules. Use the independent web interface for the integrated Week 8 RAG workflow.

## Deploying to Vercel

The existing Vercel project is connected to `yihanc09/sql-quiz`, branch `main`, with the repository root as Root Directory. A new deployment can import either complete repository, but pushing to a repository that is not connected will not update the current website.

The entrypoint is configured in [pyproject.toml](pyproject.toml):

```toml
[tool.vercel]
entrypoint = "web_server:handler"
```

`app.py` is the original Streamlit launcher, not the Vercel HTTP entrypoint. `web_server.py` exports the HTTP handler from `sql_quiz/web.py`; importing it does not start a listening server. The handler serves frontend assets and `/api/*` routes.

- Use the **Other** framework preset if needed.
- Leave Build Command, Install Command, and Output Directory at their defaults. Do not use a server-start command as a build command or set the output directory to `frontend`.
- `.python-version` selects Python 3.12. `pyproject.toml` lists backend runtime dependencies; `requirements.txt` also provides Streamlit and pytest for local development.
- `vercel.json` allows up to 60 seconds per invocation and excludes local secrets, tests, documentation, caches, migrations, and administrator tools. Runtime code, frontend assets, and schema metadata remain available; offline expected-result fixtures are not needed for live grading.

### Production environment variables

Set `DATABASE_URL` and `DATABASE_PASSWORD` for the trusted backend. For the Week 8 cloud workflow, also add these **eight separate variables**, using the configuration table above for their values:

```text
OPENAI_API_KEY
OPENAI_MODEL
CHROMA_MODE
CHROMA_API_KEY
CHROMA_TENANT
CHROMA_DATABASE
CHROMA_HOST
CHROMA_CLOUD_COLLECTION
```

Use `CHROMA_MODE=cloud`. API keys belong in backend Secret variables. Select the intended Production/Preview environments, save, and redeploy. An `.env` import creates one variable per line, not one combined variable. This project's ignored `.local/deployment.env` is a private convenience export; it is not required or supplied in a clone. Keep existing database settings when importing the RAG settings.

After private-settings initialization, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `QUIZ_DATABASE_URL`, and `APP_SESSION_KEY` do not need separate Vercel variables. Legacy overrides take precedence if present; remove stale overrides when intentionally switching to private-table configuration. The stored session key remains stable across function instances. Vercel provides `VERCEL=1` automatically.

Use Supabase's IPv4-compatible **Session pooler on port 5432** with `sslmode=require` for both backend and reader connections. This application relies on prepared statements; use the session connection rather than the transaction pooler on port 6543. Keep the password outside the backend URI and pass it through `DATABASE_PASSWORD`, including passwords with special characters. Do not replace the trusted backend connection with the reader connection: the backend must read private settings and append audit events.

The cloud index must already be populated. No local `.chroma/` directory or embedding-model weights are used in production. After redeploying, check sign-in, live Hint, Run query, Save draft, Submit answer, restored progress, and Knowledge → Generate SQL. See [deployment instructions](docs/guides/setup-and-operations.md#deploy-to-vercel) and [production verification](docs/evidence/deployment-verification.md).

## Notes and limitations

- This is a practice quiz: answers can be revised, and instructor reference SQL is intentionally available for learning. It is not a locked examination system.
- AI-generated SQL can be incorrect. Review its tables, joins, units, and ordering before running or submitting it. Generation does not run, save, or grade an answer automatically.
- The standalone Python listener is for local testing. Production uses Vercel Python Functions; public deployments still need appropriate rate limiting and operational monitoring.
- Private runtime settings contain reader credentials and a session key. Keep the trusted backend database password and API keys private.
- Audit logs retain submitted SQL for instructor review. Do not include passwords or other secrets in quiz answers.
- Database administrators can change grants or disable triggers. The append-only controls protect against student-role edits; they are not cryptographic tamper proofing.
